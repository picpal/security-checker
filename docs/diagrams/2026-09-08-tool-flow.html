secscan 파이프라인 지도

secscan scan 한 번이 어떤 순서로 무슨 도구를 돌리고, 그 결과를 어떤 조건으로 걸러 최종 판정에 이르는지를 코드 기준으로 정리했다. 각 단계에 실행 도구·실행 조건·판정 기준을 함께 적었다. 원칙은 하나다 — 도구 실행·정규화·도달성·판정은 전부 결정적 코드이고, Claude 는 확인질문에 답을 다는 증거 해석자일 뿐 판정 주체가 아니다.

2026-09-04 자 2026-09-04-scan-pipeline-flow.html 이 "왜 이 순서인가"(설계 근거)를 다뤘다면, 이 문서는 "어느 단계에서 어떤 툴이 무엇을 근거로 결론을 내는가"를 다룬다.

01실행 흐름 — 단계마다 무엇이 돌고 무엇으로 거르는가

번호는 실제 실행 순서다(secscan/scan.py run_scan). 테두리가 강조된 노드는 건너뛸 수 있는 관문(조건 불충족 시 그 단계만 생략되고 나머지 결과는 그대로 유효), 마지막 노드는 바깥으로 나가는 산출물이다.

  1. 00

    대상 스택 감지

    secscan/detect.py · secscan detect
    외부 도구 없음 — 파일 존재 검사
    조건
    루트의 pom.xml → maven, build.gradle(.kts) → gradle. 루트에 없으면 하위 모듈까지 탐색
    기준
    build·node_modules·fixtures·testdata 등은 감지에서 제외 — "주 스택"만 본다
    산출
    감지 결과로 프로파일 추천. 자연어 요청 해석은 Claude, 스택 판정은 이 코드
  2. 01

    프로파일 → 어댑터 확정

    secscan/profiles.py
    quickaccurate-scastandarddeep
    조건
    프로파일 이름이 곧 어댑터 목록 + 도달성 on/off 선언 (§4 매트릭스 참조)
    기준
    quick 만 trivy fs(속도), 나머지는 BOM 기반 SCA(전이 의존성 recall)
  3. 02

    스캐너 병렬 실행

    secscan/orchestrator.py · adapters/*.py
    trivycdxgensemgrep gitleaksspotbugs+findsecbugs
    조건
    ThreadPool min(어댑터 수, 8) 동시 실행. 도구별 타임아웃: gitleaks 300s · BOM-SCA/spotbugs 900s
    기준
    성공 판정은 도구별 종료코드 화이트리스트 — trivy·semgrep {0}, gitleaks·osv-scanner {0,1}(1 = 발견됨 = 성공)
    실패
    미설치·타임아웃·빌드실패는 예외를 올리지 않고 status=skipped/timeout/failed 로 격리 → 부분 실패로 보고하고 나머지는 계속
  4. 03

    정규화 → typed Finding

    secscan/normalize/<tool>.py
    도구 출력(JSON/SARIF) → 내부 모델
    기준
    CWE 표기를 전 도구 "CWE-NNN" 으로 통일. semgrep 은 metadata.cwe / owasp / confidence, trivy 는 CVE·컴포넌트·수정버전, gitleaks 는 위치만(비밀값은 저장하지 않음)
    주의
    SARIF 는 출력 전용이다 — 내부 정본은 항상 typed Finding
  5. 04

    합의 병합(dedup)

    secscan/normalize/merge.py
    dedup_key 동일 → 1건
    조건
    SCA 는 ecosystem|package|version|advisory, 코드 위치형은 category|file|line|rule_id
    기준
    severity 는 최대값, confidence 는 최소값(보수적), cwe·owasp·참조는 합집합, tool 은 "a+b", consensus.score = 지목한 도구 수
  6. 05

    경로 제외

    secscan/exclude.py
    기본 제외 13종--exclude.gitignore
    조건
    build target .git .gradle node_modules dist out .venv __pycache__ .idea … + 사용자 지정 + git 이 무시하는 경로
    기준
    스캐너별 제외 옵션이 제각각이라 정규화 후 경로로 한 번에 거른다. 제외 건수는 요약에 명시
  7. 06

    도달성 분석 (관문)

    reachability/engine.py · depscan.py
    OWASP dep-scanatom
    조건
    4중 안전장치를 순서대로 통과해야 실행: ① doctor 런타임·메모리 점검 → ② 소스 5만 LOC 초과면 중단(--allow-large 로 강행) → ③ 코드 해시 캐시 적중 시 재사용 → ④ 예산 600s
    기준
    atom usage 슬라이스에서 앱 코드가 실제 호출한 타입을 뽑아 취약 패키지 prefix 와 대조 — 일치하면 reachable(+"앱 코드가 X 사용" 증거), 불일치면 unreachable, 슬라이스에 없으면 unknown 유지
    실패
    타임아웃·에러·크기초과 → reason=timeout|error|size|env 로 도달성만 생략, 탐지 결과는 100% 보존

    시크릿 유효성 검증 (관문·기본 off)

    trufflehog
    조건

    기준
    trufflehog filesystem --only-verified 가 살아있다고 표시한 파일의 시크릿만 verified=true + severity critical 승격

    기준

    기준

02판정 규칙 — "조치대상"은 무엇으로 결정되는가

단계 09 의 규칙은 위에서부터 순서대로 적용되고, 먼저 걸리는 규칙이 이긴다 (secscan/disposition.py, models.sast_tier). 도구가 매긴 severity 는 이 규칙의 입력일 뿐, 그 자체가 결론이 아니다.

1 사람이 확정한 억제가 붙어 있다 억제됨 · P5
2 SAST · 경로가 테스트/로드테스트다 (/test/, loadtest, *Test.java …) 검토후보 · P3
3 SAST · 룰 신뢰도 high|medium 그리고 severity critical|high|medium 조치대상 · P1/P2
4 SAST · 신뢰도가 없거나 낮다 — 검증 안 된 룰은 우선 버킷에 넣지 않는다 검토후보 · P3
5 SCA · 도달성이 unreachable 이 아니다 (reachable 또는 unknown) 조치대상 · P1/P2
6 SCA · 도달성이 unreachable 로 확정됐다 강등 · P4
7 Secret 등 도달성 개념이 없는 범주 — 항상 조치 조치대상 · P1/P2

우선순위 P1~P5

  • P1 조치대상 & severity 심각/위험
  • P2 조치대상 & 그 외 severity
  • P3 검토후보(사람 확인 필요) 또는 미판정
  • P4 강등 — 도달 불가 SCA
  • P5 억제됨

담당 배정(보고서)

  • 자동 수정(LLM) 조치대상 & 코드 문맥 확인이 불필요한 룰
  • 사람 확인 후 조치대상이지만 문맥이 필요한 룰, 그리고 모든 검토후보
  • 자동 수정 가능(비차단) 강등 & 조치가 "버전 올리기"
  • 조치 불필요(모니터링) 강등 & 그 외
  • 억제됨 P5

"사람 확인 후" 로 배정된 항목은 자동으로 2_확인질문 시트와 report-request.json 에 실린다. 도달 불가인데 호출 경로 증거가 비어 있는 SCA 도 같은 경로로 질문이 만들어진다.

03도구별 실제 실행 — 명령 · 성공 조건 · 산출

새 스캐너를 붙이는 비용이 어댑터 1개인 이유가 여기 있다 — 코어는 RawResult 만 알고, 도구의 종료코드 관습·타임아웃·실패 격리는 각 어댑터 안에서 끝난다.

trivy fs

SCA · quick
trivy fs --scanners vuln --format json --quiet <target>
본다
Maven/Gradle 의존성 선언·락파일을 정적 파싱
성공
exit 0 만 (취약점이 있어도 0)
산출
CVE/GHSA · 컴포넌트 · 수정 버전
한계
락파일 없는 gradle 의 전이 의존은 못 본다 → BOM-SCA 로 보완

cdxgen → trivy sbom

SCA · 정확 프로파일
cdxgen -t java -o bom.json <target> trivy sbom --format json --quiet bom.json
본다
빌드도구를 호출해 만든 CycloneDX BOM = 전이 의존성 전체 그래프
조건
BOM 은 경로 해시 캐시에 1회만 생성(동시 어댑터도 한 번). 타임아웃 900s
실패
BOM 생성 실패 시 skipped — SCA 만 빠지고 스캔은 계속
효과
락파일 없는 gradle 프로젝트에서 SCA 탐지 0 → 34건

semgrep

SAST

본다
소스 코드 패턴(파일 내). 공개 룰팩 4종 + 프로젝트 커스텀 룰을 항상 함께 로드
성공
exit 0 만
산출
rule_id · CWE · OWASP · confidence — 이 confidence 가 tier 를 가른다
한계
CE 는 함수 간 taint 추적이 없다 — 대신 커스텀 룰 + 확인질문으로 메운다

secscan/rules (자체 룰 4종)

SAST · 갭 보완
mybatis-sqli-value ERROR / HIGH mybatis-sqli-identifier WARNING / LOW hardcoded-credential ERROR / HIGH zero-salt ERROR / HIGH
규칙
MyBatis ${} 는 위치로 분기 — 값 자리는 조치대상, 식별자 자리는 검토후보

룰 metadata 에 cwe·confidence 필수 → tier·컴플라이언스가 자동으로 따라온다
근거
공개 룰팩·gitleaks 가 놓친 실제 미탐 사례를 취약 시점 커밋으로 실증해 추가

SECRET

본다

SECRET 검증 · opt-in

OWASP dep-scan + atom

도달성 판정

본다
atom usage 슬라이스 — 앱 소스가 실제로 호출/참조하는 외부 타입 집합
기준
취약 패키지의 Java 패키지 prefix 와 호출 타입이 일치 → reachable, 없으면 unreachable
한계
앱 레벨 호출 기준이다. 리플렉션·DI·전이 의존 내부 호출은 사각지대 — "도달 불가"는 안전 보증이 아니다

spotbugs + findsecbugs

SAST · deep

조건

빌드 실패 시 skipped 로 격리 — deep 만 빠지고 다른 스캐너 결과는 보존
효과

상태

성공
exit 0 또는 1 (1 = 취약점 발견 = 정상)
쓸모
OSV.dev advisory 커버리지 보강 — 켜면 합의 병합으로 trivy 와 한 건으로 합쳐진다

05표준·컴플라이언스가 붙는 위치

"OWASP" 는 이 파이프라인에서 세 곳에 등장하는데, 서로 다른 것이다. 혼동이 잦아 따로 떼어 적는다.

OWASP 라는 이름이 붙는 세 지점

  • p/owasp-top-ten — semgrep 공개 룰팩. 탐지 규칙으로 단계 02 에서 실행된다
  • Finding.owasp — semgrep 룰 metadata 를 그대로 옮긴 분류 라벨. 판정에 쓰이지 않는다
  • OWASP dep-scan — 단계 06 의 도달성 엔진. 취약점을 탐지하는 도구가 아니다

KISA · PCI-DSS 는 CWE 에서 파생

KISA 소프트웨어 보안약점(49개)과 PCI-DSS v4.0.1 §6.2.4 는 기계가독 룰셋을 공식 제공하지 않는다. 그래서 별도 탐지 룰을 만들지 않고, 도구들이 이미 채운 Finding.cwe 를 허브로 역매핑한다.

도구 출력→ CWE-NNN→ KISA 49 (7대 분류) PCI 6.2.4 (5유형)

결과는 판정이 아니라 분류이며 순수 결정적이다. 코드 레벨 대응이 흐린 CWE 는 일부러 비워 둔다(과대 매핑 금지). 새 표준을 붙이는 비용은 compliance.py 표에 한 줄이다.

06보고서 워크북과 LLM 경계

스캔 결과를 사람이 읽고 수정 LLM 이 실행할 수 있는 문서로 바꾸는 마지막 구간이다. 이 구간에서도 수치·판정·담당·우선순위는 전부 규칙 파생이고, Claude 가 쓰는 것은 "추정과 확인 방법" 두 문장뿐이다.

findings.json→ 지식베이스 + 파생 규칙→ report-request.json→ Claude 해석→ 검증 통과분만 병합→ 5 시트 워크북→ 수정 LLM→ --check-result
  • 지식베이스 룰 설명은 스캔 때 생성하지 않는다 — rules.json(등록 룰) 우선, 없으면 CWE 표·advisory 로 합성. 같은 룰은 언제 돌려도 같은 설명
  • 요청 파일 사람 확인이 필요한 항목만 담는다. 항목마다 위치·룰·질문·사실 목록. 비밀값·코드 스니펫은 담지 않는다
  • 해석 검증 인용(경로:줄) 없는 답, 길이 초과, 판정 단어("오탐 확정"·"안전함"·"문제 없음"·"억제함"·"수정 완료"), 추정에 섞인 숫자, 모르는 ID 등 8가지 사유로 거부 — 거부된 항목은 조용히 버려지지 않고 사유가 기록된다
  • 완료 확인 secscan report --check-result 가 4_결과반환 시트의 "고쳤다" 주장과 재스캔 결과를 대조 — 여전히 같은 ID 가 나오면 불일치로 exit 2

워크북 5 시트

시트주 독자담는 것
0_요약경영·보안총계, 판정 분포, 스캐너 상태, 각 시트 안내
1_취약점 목록개발·보안ID·우선순위·문제·위치·의존 경로·담당·조치·근거
2_확인질문사람문맥이 필요한 항목의 질문과 사실 목록
3_용어와 대응모든 독자P1~P5·담당·판정·심각도·조치 유형을 일반어로
4_결과반환수정 LLM → 사람처리 결과를 적어 되돌려 주는 표 + 규칙 안내
