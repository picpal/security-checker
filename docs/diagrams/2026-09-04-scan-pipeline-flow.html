01 · Swimlane · to-be (§7.4)

to-be 파이프라인 — 판정 단계 H 를 둔 재구성 순서

읽는 법. spec §7.4 의 재구성 순서 입력 정책 → 수집 → 정규화 → 제외 → 병합 → 보강(도달성 ‖ 시크릿 검증) → 억제 → 판정(H) → 출력 을 01~09 로 매겼다. 각 노드 3행은 그 단계를 지금 담당하는 파일, 4행은 V4 에서 바뀌는 것이다. 판정 H(08)는 억제 다음에 오는 결정적 단계로, Finding.disposition(actionable / review / demoted / suppressed)과 Finding.tier(sast_tier 결과)를 저장하고 compliance 계산도 여기로 옮긴다. 규칙은 현행 exit code·markdown 버킷을 그대로 옮기되 억제를 먼저 본다: suppression 있음 → suppressed; SAST → sast_tier; SCA → reachability ≠ unreachable 이면 actionable 아니면 demoted; secret → actionable. exit code = any(f.disposition == "actionable"), markdown·SARIF·xlsx 는 disposition/tier 필드만 읽는다(재계산 금지). 06 보강의 두 갈래는 서로 독립(‖)이며 각각 프로파일·플래그 조건이라 점선으로, 07 억제도 baseline/억제 파일이 있을 때만 작동하므로 점선으로 그렸다. 04 제외의 위치(병합 앞)와 어댑터에 제외 패턴을 전달하는 것은 §13.2 백로그라 V4 코드는 현행 순서(병합 뒤 제외)를 유지한다 — 그림은 §7.4 가 적은 목표 순서다. 경계선 왼쪽 두 노드는 Claude·사람의 몫이고 캠페인 비범위(§2)다.

as-is → to-be · §7.4 · §13.2 · §13.3

as-is 와의 차이 (현행 12단계는 부록 A)

  • (a) 판정 단계 신설. "조치 대상인가"가 현재 세 곳에서 따로 계산된다 — exit code(cli._has_actionable), markdown 버킷(priority/review/low), SARIF sastTier. 이미 어긋나 있다: markdown 은 억제된 finding 을 active 에서 빼지만 _has_actionable 은 suppression 을 보지 않아 사람이 확정한 억제된 secret 이 있어도 exit 1(테스트 없음, §13.3 알려진 결함 → V4 에서 해소).
  • (b) tier 저장 · compliance 이동. 현행 tier 는 출력 시 매번 계산·미저장이라 findings.json 에 빠지고, compliance 는 파이프라인 중간(현행 07, 제외 직후)에서 저장된다. V4 는 둘 다 H 에서 계산해 Finding 에 저장하고, enrich_compliance 의 in-place 변경도 새 리스트 반환으로 맞춘다(결과 동일, 위치만 통일).
  • (c) 제외 위치 · 어댑터 전달은 §13.2 백로그. 제외를 병합 앞으로 옮기고 semgrep --exclude · trivy --skip-dirs · gitleaks 설정으로 패턴을 넘기는 것은 성능·위생 항목(결과 불변)이라 이번 캠페인 밖. 현재는 build/·node_modules 까지 스캔한 뒤 버린다.

V4 테스트(§7.4): 억제된 secret 만 있을 때 exit 0 · 네 출력의 actionable 집합 동일(축 8) · V1 증거 재입력 시 disposition 이 markdown 버킷과 1:1 일치(억제 케이스만 차이 = 결함 수정) · findings.json 에 disposition·tier 포함.

02 · Data flow

스캐너별 탐지 원리와 구조적 한계

읽는 법. 네 탐지기는 서로 다른 입력(BOM · 디렉토리 · 소스 · .class)을 보지만 모두 같은 typed Finding으로 정규화된다. 도달성은 새 finding을 만들지 않는다. SCA finding의 component(package@version)를 읽어 앱 코드의 usage slice에 그 패키지 프리픽스가 있으면 reachable, 없으면 unreachable을 돌려주고, 판정이 없는 컴포넌트는 unknown으로 남는다. SCA는 quick 프로파일에서만 BOM 없이 trivy fs를 쓴다. SAST의 커스텀 룰 4개 파일은 MyBatis ${} value(HIGH) · identifier(LOW), 하드코딩 자격증명(CWE-798/259), zero-salt(CWE-760)이며 semgrep 기본 팩(p/java · p/security-audit · p/owasp-top-ten · p/cwe-top-25)과 함께 항상 로드된다. 그림 전체가 결정적 코드다. Claude는 이 결과를 읽기만 한다.

03 · Flowchart

검증 캠페인 흐름 — 스냅샷 격리에서 백로그까지

읽는 법. 스냅샷은 git clone --local로 스냅샷마다 새 디렉토리에 받는다(BOM 캐시 키가 대상 경로 해시라 같은 경로를 재사용하면 stale BOM을 쓴다, §4.1). 빌드는 임의 코드 실행이므로 별도 GRADLE_USER_HOME, 크리덴셜 환경변수 제거, --network-off, 의존성 다운로드 네트워크만 허용한 "격리 실행"이다. 실행은 현행 바이너리(모델 변경 전)로 하고, 단계 추적기가 각 단계 뒤 (stage, count, dedup_keys)를 기록한다: raw:<tool> → normalize:<tool> → merge → exclude → compliance → reachability → secret_verify → baseline → suppress → final (§4.2, 현행 scan.py 순서). V4 이후에는 suppress 뒤에 disposition 단계(§7.4)가 추가된다. V1 증거 동결은 현행 바이너리 기준이라 이 단계 없이 기록하고, V4 회귀 시 두 추적을 나란히 둔다. 하네스는 이를 attrition 표로 그려 "스캐너가 못 잡음"과 "정규화·제외가 버림"을 구분한다. 증거(raw JSON·SBOM·attrition·sarif·md·도구/DB 버전·소요시간·피크 메모리)는 docs/verification/evidence/<date>/<snapshot>/에 동결되고, §7 모델·출력 변경 뒤에는 같은 증거를 재입력해 회귀한다(baseline 이동 방지, §4.4). 실스캔 재실행은 xlsx 완성 후 1회. 정답지 2종은 대조기로 들어온다. GT-B(46건)는 SCA 매칭 순서 exact → version-mismatch → alias(OSV aliases에서만 유도) → missed, 기대 absent가 매칭되면 false-positive, 초과 탐지는 team-missed / db-drift / inventory-diff / our-fp 4분류(공개일 없으면 unknown-date, §4.3). GT-A는 취약 스냅샷 4개와 수정 커밋 쌍으로 들어와 축 7 differential(출현 ∧ 소멸)에 쓰인다. 게이트 미통과는 캠페인 실패가 아니라 백로그 P1 등록 사유이고, 전 축의 수치는 통과 여부와 무관하게 측정 문서에 기록된다(§5). 그림 전체가 결정적 코드다(Claude 층은 비범위, §2·§10).

05 · Data flow

출력 확장 — typed Finding → findings.json → projection 계약 → md / SARIF / xlsx

읽는 법. 모델 확장(§7.1): Occurrence(tool, target, package, version)를 merge가 union해 Targets·Finding Count를 복원하고(현재는 첫 finding의 source만 유지), Cvss(source, version, score, vector)로 trivy의 nvd/redhat/ghsa를 전부 보존해 Max CVSS Score·CVSS Source는 출력 시 파생한다. severity는 계속 벤더 등급(CVSS로 재계산 금지). Advisory.published는 초과분 분류용, ScanResult.scanner_status(name·status·tool_version·duration_s·message)는 구성된 어댑터 이름 대신 실제 status를 보고서에 넘기기 위한 것이다. 출력 전 안정 정렬은 (category, severity rank desc, reachability rank desc, dedup_key). findings.json(§7.2)은 SARIF가 아니라 내부 모델의 완전 직렬화이며 SARIF는 여전히 출력 전용이다(원칙 3). 판정 H(§7.4)가 저장한 disposition·tier 를 네 출력이 그대로 읽고(재계산 금지), exit code 는 any(f.disposition == "actionable") 하나로 결정된다 — 억제된 finding 이 exit code 를 올리던 현행 결함(§13.3)은 여기서 사라진다. projection 계약(§7.3, docs/output-contracts.md)은 포맷별 포함/손실 필드(SARIF: aliases · references 일부 · source · verified · suppression basis)를 표로 못 박고, markdown finding 줄에 id(12 hex)를 추가한다(억제 스코프 지정용). xlsx(§8): pip install secscan[xlsx] → openpyxl, 미설치 시 시트별 CSV 번들 + 경고 1줄, 코어 의존성 0 유지. Deduped_CVEs의 보안팀 12열은 No. · Vulnerability ID · Severity · Max CVSS Score · CVSS Source · Affected Packages · Installed Versions · Fixed Versions · Targets · Finding Count · Title · URL, secscan 9열은 도달성 · 도달성 근거 · 합의 도구 · 합의 점수 · 조치 등급 · KISA · PCI · 억제 상태 · Finding ID. 방어: 셀 값이 = + - @(선행 공백·제어문자 뒤 포함)로 시작하면 ' 접두 + 문자열 타입 강제, 32,767자 초과 절단 + …[truncated], 불법 XML 문자 제거, 1,048,576행 초과 시 시트 분할. CSV 폴백도 같은 sanitizer. 결정성: 정렬 고정, workbook created/modified를 스캔 일시로 고정. 골든: 시트 4종·헤더 12개 스키마(사진 기준 재구성) 대비 검사 + openpyxl 재오픈 왕복.

codex review → spec

Codex 검토에서 바뀐 핵심 5가지

  1. 분모 34 → 46. 34/35는 기존 trivy 결과 재현율이지 recall이 아니다. 보안팀 35행 + 개발자 추가 발견 12(tomcat 11 + logback 1)를 정답지로 삼고, "precision" 대신 known-FP 회귀 + 초과분 전건 분류로 이름을 바꿨다. → §3.2, §5 축 2·4
  2. 도달성 축 재정의 · false-unreachable. 현 엔진(패키지 prefix 존재)과 사람 판정(CVE별 활성화 조건)은 의미가 달라 일치율은 무의미하고, "human unreachable일 때 reachable 안 하기"는 전부 unreachable로 답하면 만점이 되는 잘못된 지표다. 판정 근거 비교표 + paired 픽스처 + false-unreachable = 0 + unknown 기권 비율로 바꿨다. → §5 축 6, §6
  3. historical / current 분리. trivy DB는 임의 날짜로 고정할 수 없고(--skip-db-update는 현 캐시 재사용일 뿐) 당시 raw JSON·캐시가 없어 역사적 재현은 폐기했다. "현재 DB 기준 유효성"을 재고 35행과의 차이는 team-missed / db-drift / inventory-diff / our-fp로 설명한다. → §4.3, §2 비범위
  4. occurrences · CVSS map. merge가 첫 finding의 source만 남겨 Targets·Finding Count·복수 패키지 집계를 복원할 수 없었고, CVSS를 단일 score/source로 두면 다시 정보가 손실된다. Occurrence union과 source별 Cvss(version·score·vector) 보존, Max CVSS Score는 출력 시 파생, severity는 벤더 등급 유지로 바꿨다. → §7.1
  5. openpyxl extra. stdlib zipfile로 XLSX를 자작하면 OOXML escaping·styles·shared strings·결정적 ZIP 메타·Excel 호환성을 떠안게 된다. openpyxl을 extra(secscan[xlsx])로 두고 미설치 시 CSV 번들 폴백, 코어 의존성 0 유지 + formula injection·셀 한도 방어를 명시했다. → §8

그 밖의 Codex P1(측정 단위·alias 매칭, 단계별 attrition, 12열 스키마 골든, lossless 왕복 vs projection, GT-A 매니페스트·detection/actionable 분리·differential, 억제 변이 기대값, partial failure 보고·프로파일 드리프트·BOM 캐시·격리 실행·게이트 수치·증거 동결 순서)은 spec §12 반영표에 절 번호로 대응돼 있다.

§13.1 · 공통 규칙 — 원칙 2 를 지키는 형태는 하나다

LLM 이 검사를 작성하고, 결정적 파이프라인이 실행한다

  1. (a) 핫패스 밖. 파이프라인 종료 후 findings.json 을 입력으로, 배치·캐시(키 = advisory 또는 dedup_key × 코드 해시).
  2. (b) 결정적 산출물에 미혼입. json · SARIF · xlsx · exit code 에 LLM 텍스트를 섞지 않는다 — 별도 파일에 출처 표기.
  3. (c) 방향 제약. 위험을 올리는 쪽(reachable, 검토 필요)만 단독 작용. 내리는 쪽(unreachable, 억제)은 사람 확정.

금지 영역: 정규화 · 병합 · 제외 · 판정(H) · 시크릿 검증에는 넣지 않는다(FN · 비결정성).

읽는 법 (후보 1). LLM 은 advisory 본문에서 전제조건(polymorphic typing 활성화, HTTP/2, SiftingAppender, log4j-core 존재 등)을 뽑아 grep · semgrep · 설정 키 쿼리만 만든다. 실행은 결정적 파이프라인이 하고 증거는 (쿼리, 결과, file:line) 로 남는다. 발견이면 reachable — 위험을 올리는 쪽이라 단독 작용을 허용한다. 미발견이면 unknown + 증거로 끝나고, unreachable 이나 억제처럼 위험을 내리는 판단은 사람이 확정한다(규칙 (c), 원칙 4). 이 자리가 Reachability.source = "claude" 다. message-gate 사람 판정 18건이 전부 이 유형이라, 축 6 이 "config-gated = unknown" 으로 끝나면 다음 사이클 1순위.

01의도 해석(Claude)자연어 요청을 intent(quick · patch · sca · full · standard · deep)로 해석. 경계 밖, 비결정적.
02스택 감지 · 프로파일 추천detect.py · cli.py:_cmd_detectsecscan detect --target --intent 별도 서브커맨드. pom/gradle·java/kotlin 감지 후 intent→프로파일 표로 추천만 출력. scan은 이 함수를 호출하지 않는다.
03프로파일 → 어댑터 구성profiles.py · cli.py:_cmd_scan--profile(기본 accurate-sca)로 어댑터 인스턴스 생성. 도달성 provider(캐시 디렉토리 = 소스 해시), 시크릿 정책, 억제·baseline 파일 로드도 여기서 결정.

10baseline → 억제suppress/store.py · suppress/engine.py--baseline 먼저(기존 키 → state=baseline), 그 다음 --suppressions(scope = dedup_key 정확 매칭). 만료되었거나 unreachable 근거가 reachable로 바뀌면 억제를 풀고 invalidated로 보고. 자동 억제 없음(원칙 4).

reachability/engine.py

도달성 4중 안전장치 (적용 순서)

  1. 환경 점검 — depscan · java · node 없으면 reason=env로 생략.
  2. 크기 인지 — LOC > 50,000이고 --allow-large가 아니면 size.
  3. 캐시 — 소스 해시가 같으면 이전 결과 재사용(cache).
  4. 예산 · 폴백 — provider 600초 초과 → timeout, 예외 → error.

어느 경우든 탐지 결과는 그대로 남고 도달성만 unknown으로 남는다. 코드 주석 번호(④→①→②→③)와 실제 적용 순서가 다르므로 위는 적용 순서로 적었다.

verified against code

흔히 말하는 순서와 코드가 다른 곳

  • detect는 scan 파이프라인 안에 없다. secscan detect는 추천만 출력하는 별도 명령이고, secscan scan은 --profile 값을 직접 받는다(02→03 점선).
  • 컴플라이언스 매핑은 마지막이 아니라 07이다. 경로 제외 직후, 도달성·시크릿 검증·억제보다 앞서 항상 실행된다.
  • SAST tier는 파이프라인 단계가 아니다. models.sast_tier()는 finding을 바꾸지 않는 순수 함수로, 11단계(markdown 섹션 분류 · SARIF sastTier · exit code)에서만 호출된다.
  • 억제는 baseline → 명시 억제 순. 이미 baseline으로 억제된 finding에는 명시 억제가 덮어쓰지 않는다.
  • 커스텀 룰은 4개 파일. MyBatis ${}가 value(HIGH)와 identifier(LOW)로 나뉘어 3종 = 4파일이다.
