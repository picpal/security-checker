# 보안 점검: $ARGUMENTS

## 사전 조건

`.venv/bin/secscan` 이 없으면 **`/secscan-setup` 을 먼저 실행하라고 안내하고 멈춘다.**
(급하면 `python3 -m secscan` 으로도 동작하지만, 스캐너가 갖춰졌는지는 확인되지 않은 상태다.)

## 1단계 — 대상 확보

`$ARGUMENTS` 가 비어 있으면 **점검 대상을 묻는다.** 기본값을 추측하지 말 것 —
현재 디렉터리는 secscan 도구 자신이라 점검 대상이 아니다.

인자가 `https://` · `http://` · `ssh://` · `git://` 로 시작하거나 `user@host:path` 형태면 git URL 이다.

**git URL 인 경우:**

```bash
.venv/bin/secscan fetch <URL>
```

출력의 클론 경로와 커밋 SHA 를 기록해 둔다. 이후 `<대상>` 은 그 클론 경로다.
이미 받아 둔 클론이 있으면 secscan 이 지우고 다시 받는다 — 항상 현재 기본 브랜치 기준이다.
클론이 실패하면 여기서 멈추고 사유를 그대로 전한다(비공개 repo, 오타, 인증 등).

**로컬 경로인 경우:** 그대로 `<대상>` 으로 쓴다. 경로가 없으면 멈추고 알린다.

`<슬러그>` 는 git URL 이면 fetch 가 만든 디렉터리 이름, 로컬 경로면 그 디렉터리 이름이다.

## 2단계 — 스택 감지

```bash
.venv/bin/secscan detect --target <대상> --intent full
```

"JVM 프로젝트로 보이지 않습니다" 경고가 나오면 **사용자에게 알리고 계속할지 묻는다.**
secscan 은 JVM 타깃이라, 다른 언어면 secret 점검 외에는 결과가 거의 비어 있을 것이다.

## 3단계 — 프로파일 결정

detect 의 추천을 기본으로 쓴다.

- 추천이 `quick` / `accurate-sca` / `standard` → **묻지 말고 그대로 진행**
- 추천이 `deep` → **반드시 확인받는다.** deep 은 대상 프로젝트를 실제로 빌드하므로
  수 분~수십 분이 걸리고, 빌드 실패 가능성이 있다. `standard` 로 낮추는 선택지를 함께 준다.

사용자가 프로파일을 직접 지정했으면 그 말을 따른다.

## 4단계 — 점검 실행

```bash
.venv/bin/secscan scan --target <대상> --profile <프로파일> --out out/<슬러그>
```

시간이 걸린다. 오래 걸릴 수 있다고 미리 알린다.

**exit code 1 은 실패가 아니라 "조치 대상이 있음" 이다.** 실패로 보고하지 말 것.
exit 2 만 잘못된 사용(알 수 없는 프로파일 등)이다.

`--verify-secrets` 는 **먼저 묻지 않는 한 절대 쓰지 않는다.** 자격증명을 제3자 서비스로
전송한다. 사용자가 명시적으로 요청했을 때만 붙인다.

요약 출력에 `⚠️ 부분 실패` 가 있으면 **그대로 보고한다.** 어떤 스캐너가 죽었고 그래서
어떤 범주가 비어 있을 수 있는지 말한다. 전부 성공한 것처럼 넘어가지 말 것.

## 5단계 — 보고서 해석

`out/<슬러그>/report.md` 를 읽고 사용자에게 해석해 준다. 우선순위:

| 순위 | 대상 |
|---|---|
| 1 | secret — 실제 자격증명이면 즉시 회수·교체 |
| 2 | SCA 중 **도달 가능** — 실제로 호출되는 취약 의존성 |
| 3 | SAST 중 **우선(actionable)** tier |
| 4 | SCA 중 **미상(unknown)** — 도달성 판정 실패, 사람이 봐야 함 |
| 5 | SAST **검토후보(review)** tier · SCA **도달 불가** |

각 건에 대해 **파일을 실제로 열어 근거를 확인한다.** 보고서의 location 은 파일:라인이고,
클론은 지우기 전까지 남아 있다. 보고서 문구만 옮기지 말고 코드를 보고 말할 것.

**컴플라이언스 표기 주의:** KISA/PCI 라벨은 finding 의 CWE 에서 파생한 **분류**이지
합격/불합격 판정이 아니다. "KISA 49개 중 N개 위반" 같은 판정조로 쓰지 말 것.
"이 건은 KISA 분류상 IV-01(SQL 삽입)에 해당한다" 가 맞는 표현이다.

## 6단계 — 억제 제안

오탐으로 보이는 건이 있으면 **후보로만 제시**한다. 각 후보에 근거(왜 오탐인지, 어느 코드를
보고 그렇게 판단했는지)를 붙인다.

**절대 자동으로 억제하지 않는다.** 억제 파일을 직접 쓰지 말고, 사용자가 확정하면 그때
`--suppressions` 파일에 넣을 내용을 만들어 준다.

## 마무리

- 보고서 위치: `out/<슬러그>/report.md` · `out/<슬러그>/findings.sarif`
- git URL 을 받았으면 클론이 `.secscan/repos/<슬러그>` 에 남아 있다고 알리고,
  `/clear-clone` 으로 정리할 수 있다고 안내한다
